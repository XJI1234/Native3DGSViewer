# SPZ v4 解码算法与本机验证

2026-10-25；preview.4。环境：Windows、Edge 156.0.4314.42、NVIDIA Ampere
（本机 RTX 3080），Node 24.14.1、Emscripten 6.0.11、固定 SPZ/zstd 子模块。
模型不随源码或 SDK 分发。复现命令和逐项结果见
[证据目录](evidence/spz-v4-2026-10-25/results.json)。

## 仓库边界

根目录为 Windows C++20/D3D12/WinUI 引擎；ForAndroid 以 Vulkan/JNI/Kotlin
复用平台无关解码与规范化；ForServer 是 CUDA worker、Go 网关、SQLite 缓存与
图像客户端；CudaOperators 是 CUDA 互操作/算子实验。ForWeb 独立拥有 TS SDK、
Worker、WASM 适配层、WebGPU/WGSL 和 React/Vue 适配器。本轮不改变原生平台
契约、vendor 源码或 GPU ABI；保留 model-io/render-core 的依赖边界。

## 根因与源码依据

实际复现档案馆 v4 的 `ResourceLimit · Load: estimated CPU/WASM/GPU peak`。
旧策略只让 gzip SPZ 和大型 PLY 进入 OPFS，v4 调用 `loadSpz` 整模型解码：
完整压缩输入、六个解压属性数组、vendor float cloud、规范化场景和 GPU 打包页
在同一任务中重叠。增大默认 CPU 限额无法解决 wasm32 的独立线性内存上限。

| v4 文件 | 点数 / SH | 旧 WASM 峰值估算 | 旧 CPU 峰值估算 |
| --- | --- | --- | --- |
| danganguan_spzv4.spz | 1,859,737 / 3 | 1,362 MiB | 1,881 MiB |
| zhihuizhimen_spzv4.spz | 3,904,214 / 3 | 2,849 MiB | 3,986 MiB |

以上是旧代码的保守准入估算，不是实际进程 RSS。旧独立 WASM 门槛为 960 MiB，
CPU 默认为 512 MiB，所以两者在实际解码前就被拒绝。

研读与实现依据：

- 固定 [SPZ load-spz.cc](https://github.com/nianticlabs/spz/blob/5bf2945de1a003cee07133b1e495fe9c6ffdc7e7/src/cc/load-spz.cc)：
  32 字节 v4 头、uint64 TOC、五/六条连续 Zstd 属性流；Emscripten 分支串行
  `ZSTD_decompress`；`PackedGaussians` 的 v3/v4 位置、scale、SH、smallest-three
  四元数布局相同。保留其 unpack 数学，避免另写量化/旋转实现。
- 固定 [zstd.h](https://github.com/facebook/zstd/blob/794ea1b0afca0f020f4e57b6732332231fb23c70/lib/zstd.h)：
  `ZSTD_getFrameHeader` 可在分配窗口前检查需求；`ZSTD_d_windowLogMax`
  限制实际分配；`ZSTD_decompressStream` 显式返回输入消费、输出产生和帧结束。
  输出恰好填满后可能还需零输入 drain，不能把“需要更多输入”当作损坏。
- [Zstd 格式规范](https://github.com/facebook/zstd/blob/794ea1b0afca0f020f4e57b6732332231fb23c70/doc/zstd_compression_format.md)：
  普通帧、窗口、可选 checksum 与字典标识的语义。未带 checksum 的合法文件
  只能执行结构/长度/属性检查，不宣称具有不存在的校验和。
- [既有 Spark/WASM 研读](spark-decoder-source-study.md)：分块边界和内存生命周期
  决定容量；换成 Rust/WASM 或仅使用更多线程不会消除整场景数组。

## 采用的算法

1. WASM probe 后再次检查 v4 头与 TOC。uint64 用 BigInt，检查每个压缩范围、
   count×属性宽度、精确文件结尾和支持的 flags，拒绝溢出、截断、额外数据。
2. 只读取各流最多 18 字节帧头，确定最大窗口；拒绝字典/跳过帧，窗口上限
   128 MiB。把窗口计入本任务准入；两个真实样例均不超过 4 MiB。
3. 每次只保留一个 Zstd context、最多 4 MiB 输入/输出。逐属性解压到同一个
   OPFS 文件的列段，要求一段恰好一帧、输出长度精确；存在 checksum 时验证。
   窗口限额在 native decoder 再执行一次。
4. 对应位置的六个小属性片段组合成一个有界批次，调用同一 vendor unpack，
   完整保留点顺序、SH0–3、float32 和 RUB 坐标。single/pthreads 共用这条路径。
5. 原有 64 点 tile 打包到磁盘，合并全局 bounds，最后仅做一次全局 rebase；
   4 MiB 分块 GPU 上传，排序、首帧验证和事务提交仍由现有 engine 管理。
6. CPU 预算不足时按 64 点对齐收缩批次；auto 在低预算/非隔离网页选单线程。
   保留旧场景的 CPU 数据、allocator 余量、输入副本、线程栈和压缩窗口均计入。
   最小批次仍放不下时明确 ResourceLimit，不降低点数或 SH。

选择顺序属性解压＋OPFS，可以复用已经验收的批次/恢复链路，并避免同时保留
六个 Zstd 窗口。六路流同时解压并直接组成 tile 可减少磁盘 I/O，但会扩大窗口
与调度状态，留作独立实验；本版不声称 Zstd 并行解压。WASM64、直接 GPU 量化、
LoD/抽样会改变平台或质量契约，本轮没有用它们替代完整质量验收。

## 实测容量与等价性

隔离网页三种自动/单线程配置、显式 parallel 配置，以及普通非隔离网页均测试。
每个模型各配置的 count、degree、全部 bounds 与固定相机 640×360 RGBA SHA-256
一致。该哈希检验路径等价性，不能替代其他渲染器/设备的独立画质验收。

| CPU 策略 / 后端 | 每批点数 | 估算引擎 CPU 峰值 | 实测 WASM 堆高水位 |
| --- | --- | --- | --- |
| 512 MiB / single | 64,512 | 139.1 MiB | 37.2 MiB |
| 512 MiB / pthreads 4 | 64,512 | 187.1 MiB | 62.5 MiB |
| 64 MiB / auto→single | 16,128 | 62.5 MiB | 16.0 MiB |

两份 v4 都完整成功：档案馆 1,859,737 点、智慧之门 3,904,214 点，全部 SH3。
智慧之门 packed backing 为 921,404,416 字节，GPU 场景预算约
1,141,996,688 字节。GPU 与 OPFS 容量另计，64 MiB 不是浏览器 RSS 或整机 RAM
限制；没有在弱 GPU/低 RAM 物理机器上实测，不将预算模拟当成跨设备承诺。
不同版本模型点数可能不同：本机档案馆 v3 实为 1,888,950 点，不能拿它与 v4
做逐字节模型等价断言。

加载耗时、阶段和逐帧图像在 JSON 中保留；它们是单次端到端功能测量，包括
本地 HTTP、磁盘、解码、上传与首帧，不是重复性能基准或显示 FPS。没有据此
声称固定倍数提速。

## 验证与复现

从 ForWeb 运行 `pnpm run build:wasm`、`test:unit`、`test:contracts`、
`typecheck`、`lint`、`check:boundaries`、`build`。
设置 `GS_MODEL_ROOT` 到本机模型父目录，启动本地 Vite；隔离服务另设
`GS_CROSS_ORIGIN_ISOLATED=1`。执行：

```powershell
node tools/spz-v4-browser-tests.mjs
# 可指定 GS_TEST_URL 和 GS_V4_OUTPUT；普通/隔离网页各运行一次。
pnpm run test:gpu
pnpm run test:integration
pnpm run test:models
pnpm run test:sdk
```

证据目录包括原有 38 模型完整加载回归（最大 22,480,361 点）、GPU 排序/图像、
事务/设备恢复、独立安装包的 SSR/React StrictMode/Vue/卸载测试。
新增 WASM 契约覆盖 1 字节 I/O、checksum、截断、帧边界、窗口上限、SH0–3、
partial tile、全缓冲/分批和 1/2/4/8 线程数学等价。浏览器覆盖四种损坏输入、
解压阶段取消、旧场景保留和所有 job 清理。显式 parallel 防止回退掩盖增强路径
故障。公共 `snapshot.decoder` 的分配诊断只跟随实际提交场景发布。

## 仍然适用的边界

必须具备 WebGPU、HTTPS/localhost、OPFS 与足够 GPU/磁盘配额；实际 GPU 分配失败
仍会报错。私密浏览的大文件快照限制、其他浏览器/系统和移动触控要独立验收。
不支持 SPZ antialiased/未知扩展、SH4 或其他非既定格式。旧场景在替换时仍可能
增加 GPU/CPU 峰值；宿主可明确关闭旧模型后加载，但会失去失败保留旧画面的能力。
发布包必须同步更换 Worker、基础和 threaded WASM，不能混用 preview.3 资产。
