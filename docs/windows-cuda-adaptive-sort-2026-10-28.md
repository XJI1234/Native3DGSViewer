# Windows CUDA 自适应排序：逐项优化与验证（2026-10-28）

已接入按规模选择的可选 CUDA 排序。当前策略是：实际 DX12 设备通过 CUDA 探测且实际渲染点数达到 **2,000,000** 时使用 **CUB 32 位稳定基数排序 + CUDA Graph**；其余使用原 DX12 排序。视口右上角仅在当前活动场景的首个 CUDA 帧完成后显示“已启用 CUDA 加速”。静止视角继续复用排序结果。

本轮优先测试交换/提交链路。提前录制、批量屏障、去冗余完成 fence、三者组合、整个互操作区域 Graph 和归并替代方案均没有稳定的完整帧收益，实验代码已撤回。保留了现有 CUB Graph 的 CPU 提交收益，没有把小模型强制切换到 CUDA。

测试环境沿用 RTX 3080 10GB、驱动 617.42、Windows WDDM、CUDA 13.3 / CUB 3.3.3 / Release SM86。模型仍来自 `C:\Users\21544\Desktop\zhishan`，不修改源文件。

同三帧槽、1920×1080、完整点数/SH3、完整 32 位键和稳定同键次序；每次 60 帧预热、120 帧采样，两轮交替顺序。主矩阵采用固定 yaw 30°、pitch −45°、dolly 2 的原视角。指标是同一 D3D12 时间域中的投影到绘制结束的完整 GPU span，包含 CUDA 交接；CPU submit 单独统计，不以 CUDA event 或 FPS 替代完整帧。

共采集 162 次运行、19,440 个样本帧，全部图像与对应 DX12 参考字节一致。confirmation 第一轮最小模型的 4 次运行开头与一次集成测试重叠，整块计时排除，保留原始记录；有效性能运行 158 次。其余性能组没有并发 GPU 测试。短测用于本机工程取舍，不是新的正式长测验收。

17 万和 80 万点依然是 DX12 更快。125 万点 Graph 在不同组有约 0.3%–0.6% 的微小 GPU 领先，同时 CPU 提交仍较高，接近交叉区，未作为默认切换边界。391 万点的收益明显。最终取 200 万点作为保守阈值，避免把接近噪声的收益推及全部小模型。

阈值附近另测 `citang_v1`：2,116,317 点 PLY 完整 GPU 帧 **3.175424 → 3.006208 ms，降低 5.33%**；SPZ **3.170816 → 2.993920 ms，降低 5.58%**。同组 391 万点 **5.827840 → 5.255168 ms，降低 9.83%**；2248 万点 **34.835968 → 29.216512 ms，降低 16.13%**。大模型两轮波动明显，这些是本轮短测结果，不能替代旧正式测量的约 14%–15% 结论。PLY/SPZ 分别与其自身 DX12 输出比较，没有假设解码后两种格式逐点相同。

“简并排序”没有确定的标准算法定义，本轮按“小规模专用替代排序”的意图，具体测试了稳定并行归并：每个线程在相邻有序段通过 lower/upper bound 求稳定输出位置，再逐轮合并。它保留全部 32 位键和输入同键次序，并通过 0/1/511/513/65,537/170,799 项、随机/同键/逆序/重复与无效键的 CPU stable_sort 对照。该实现需要多轮全局读写和二分查找，没有减少跨 API 往返；实验结果仅否定本实现，不能推断所有归并算法都更慢。没有通过缩键、近似排序或减少渲染工作取得收益。

交换链路已经使用加载时创建/映射的共享 GPU buffer；没有每帧经 CPU/PCIe 往返搬运排序数组。单纯减少屏障 API 调用或一次 Signal，无法消除 WDDM 调度、跨队列供给和互操作依赖。CUB Graph 明显减少主机提交开销，但仍需 DX12→CUDA→DX12 交接，小模型的计算收益不足以覆盖该代价。真正独立的数据帧槽/重叠执行和全新 DX12 排序属于后续架构研究，本轮没有实现，也没有标成性能失败。

产品接入包含以下行为：

- 通过程序目录绝对路径延迟加载版本化私有 C ABI；SDK 无 CUDA 头文件/链接依赖。缺 DLL、ABI 不符、LUID 无匹配、实际探测 kernel 不可运行，均保留 DX12。
- 阈值比较实际渲染点数；小模型不建立四个场景共享排序 buffer。大模型先检查额外显存预算，分配或预热失败回退 DX12。映射、scratch、Graph 只在建立场景时分配。
- CUB 输出 selector 在预热时确定，后续绑定不变；投影保持原输入 buffer，绘制与测距读取同一个实际排序结果。场景通过帧槽持有，最终 consumer/Present fence 覆盖共享资源生命周期。
- CUDA 上下文在提交线程重新绑定实际选中设备，支持初始化线程与引擎渲染线程分离。提交失败后禁用该 renderer 的 CUDA，经设备恢复使用 DX12，不直接在未完成的共享缓冲上重试。失败运行时模块保留，避免卸载仍可能被隔离资源引用的 CUDA 代码。
- `RenderStats.cuda_available` 表示提供者在当前配置可用；`cuda_sort_active` 由当前场景已完成帧发布。清空、换成小模型、设备丢失时隐藏提示；静态复用继续显示。
- D3D12 Debug Layer 配置使用 DX12，避开已有外部 fence 退役句柄滞留问题。这是保守的产品回退，不宣称底层调试问题已修复。
- 修复原设备恢复流程：有 retained scene 正在重新上传时，不提前发出 `DeviceRestored`。恢复测试宿主也按原契约先释放旧 swapchain，再请求下一帧设备重建。

当前已通过完整 CTest 14/14 组（144.39 秒），包括独立安装/重定位 SDK、引擎、渲染、CUDA 排序/互操作/生命周期/投影/压缩/tile。正常配置隔离进程的 5 项 CUDA 产品集成测试全部执行并通过，没有跳过，覆盖阈值/换模/取消/清空、静态复用、测距、准备失败、提交失败恢复到 DX12、真实设备移除后重新探测恢复。全量 RenderCore 进程因之前已启用全局调试层，会跳过 CUDA 专属路径；其覆盖由独立 AdaptiveSortProduction 组提供。归并实验正确性记录也保留。

最终桌面构建通过。无 DLL 独立进程以 DX12 完整渲染 200 万点；真实桌面进程分别加载 170,799 点和 3,914,609 点，日志确认前者 CUDA 可用但未激活、后者已激活，两次均正常退出。提示验证覆盖状态逻辑和真实 GUI 日志，没有做截图像素检查。运行记录与源文件指纹归档在 [本轮证据](../CudaOperators/evidence/2026-10-28-adaptive-sort/README.md)。部署命令见 [GUI/README](../GUI/README.md)。默认 CUDA 构建开关仍为 OFF；可选构建把 DLL 与许可证放到 out/Release，安装器的 `-EnableCuda` 可显式构建后端。

阈值仅用本机 RTX 3080 校准；当前构建目标为 SM86 及兼容 PTX 的设备，其他设备以实际 kernel 探测为准。未执行两小时长稳、全设备矩阵或任意驱动挂起的强隔离验证；CUDA 驱动 API 自身的阻塞仍是既有边界。公开 C++ RenderStats 增加了两个字段，SDK 消费者需要重新编译。本轮不修改模型加载/解码算法，格式加载时间沿用前一份报告。
